\subsection{Measurement Approach}

The benchmark framework uses Python's \texttt{spawn} start method, placing each participant in a separate process with its own address space---the deployment model where IPC is actually necessary.

A \texttt{multiprocessing.Barrier} synchronizes startup so that all processes begin measurement simultaneously. Latency is measured end-to-end: the writer embeds a \texttt{time.perf\_counter()} timestamp in each message immediately before transmission, and the reader computes the difference upon receipt, capturing the full IPC path including serialization, synchronization, memory transfer, and deserialization. The \texttt{perf\_counter()} function maps to \texttt{clock\_gettime(CLOCK\_MONOTONIC)} on Linux, providing sub-microsecond resolution immune to NTP adjustments. Since all processes execute on the same machine, they share a single kernel clock source, making cross-process timestamp differencing valid.

To eliminate measurement noise from CPU migration, writer and reader processes are pinned to dedicated physical cores using \texttt{os.sched\_setaffinity()}. The writer occupies core~0; readers occupy cores~1 through~$N$. For scenarios where the total process count exceeds available cores (e.g., 10:1 contention on an 8-core machine), pinning is automatically disabled and processes share cores under OS scheduler control.

\subsection{Payload}

The primary payload is a \texttt{MockPipeData} structure containing three NumPy arrays of shape $640 \times 480 \times 3$ (unsigned 8-bit integers), representative of a triple-channel video frame from a computer vision pipeline. The raw data totals $640 \times 480 \times 3 \times 3 = 2{,}764{,}800$ bytes (2.64~MiB); after pickle serialization the message is marginally larger due to framing overhead.

For size-scaling experiments, raw byte buffers of 1, 2, 4, 8, 16, and 32~MiB are used to isolate the effect of payload size from serialization overhead.

\subsection{Metrics}

Four metrics characterize IPC performance:

\begin{itemize}
    \item \textbf{Median latency (p50)}: The 50th percentile of end-to-end message delivery time in milliseconds. Represents typical-case performance.

    \item \textbf{Tail latency (p99)}: The 99th percentile latency. Critical for real-time systems where worst-case behavior determines system feasibility.

    \item \textbf{Throughput}: Total bytes transferred across all iterations divided by the trial's wall-clock duration, expressed in MiB/s (binary megabytes). This is a trial-level aggregate: because iterations overlap (the writer begins the next message while the reader deserializes the current one), sustained throughput can exceed the per-message estimate $\text{size} / \text{p50}$. The ratio between them reflects the degree of pipelining in each backend's design.

    \item \textbf{Determinism ratio}: Defined as $\text{p99} / \text{p50}$. A ratio of 1.0 indicates perfectly predictable latency; higher values indicate jitter. For real-time applications, predictable latency is often more valuable than lowest average latency.
\end{itemize}

\subsection{Statistical Methodology}

Each scenario executes 10 independent trials. For the standard payload, each trial performs 200 message exchanges preceded by 20 warmup iterations whose latencies are discarded. Iteration counts scale down for larger payloads to keep execution time reasonable: $\lfloor 200 \,/\, (S / 2 + 1) \rfloor$ iterations for a message of $S$~MiB, yielding approximately 66 iterations at 4~MiB and 11 at 32~MiB. Percentiles are computed per trial using NumPy's percentile function over all post-warmup messages per reader process. The reported values represent medians across trials, with first quartile (Q1) and third quartile (Q3) available for variability assessment.

When multiple readers participate, the reported p50 and p99 represent the arithmetic mean of per-reader percentiles within each trial.

\subsection{Backends Under Test}

Seven IPC backends are evaluated, spanning Python's standard library, external libraries, and the two operational modes of \texttt{rs\_ipc}:

\begin{itemize}
    \item \textbf{RsIpc (zerocopy)}: The writer acquires a write guard and serializes directly into shared memory by calling \texttt{pickle.dump(obj, guard)}. The reader acquires a read guard and deserializes directly via \texttt{pickle.load(guard)}. No intermediate copies are created.

    \item \textbf{RsIpc (copy)}: The writer serializes with \texttt{pickle.dumps(obj)} into a temporary Python bytes object, then calls \texttt{shm.write(bytes)} which performs a single \texttt{memcpy} into shared memory. The reader receives a Rust-allocated copy of the shared memory contents and deserializes from that copy.

    \item \textbf{multiprocessing.Queue}: Python's standard thread-safe, process-safe queue. Internally uses pipes with a background feeder thread for serialization. Bounded to size 1 for fair comparison with fixed-size shared memory slots.

    \item \textbf{multiprocessing.Pipe}: Low-level bidirectional connection using OS pipes. In multi-reader scenarios, a \texttt{multiprocessing.Lock} serializes writer access to prevent interleaved messages.

    \item \textbf{multiprocessing.shared\_memory (MpShm)}: Python's native shared memory module, supplemented with manual \texttt{multi\-processing.\allowbreak{}Lock} and \texttt{multi\-processing.\allowbreak{}Condition} for synchronization. This backend replicates what a developer would build using only the standard library, and serves as a direct comparison point for the synchronization quality of~\texttt{rs\_ipc}.

    \item \textbf{ZeroMQ}: The \texttt{pyzmq} library using PUSH/PULL sockets over IPC transport (\texttt{ipc://} Unix domain sockets). Represents a mature, widely-deployed messaging library with internal threading, message framing, and batching optimizations. In multi-reader scenarios, one PUSH socket per reader ensures guaranteed delivery to all consumers.

    \item \textbf{PosixIpc}: The \texttt{posix\_ipc} package providing POSIX shared memory (\texttt{shm\_\allowbreak{}open}) with POSIX named semaphores (\texttt{sem\_\allowbreak{}open}) for synchronization. Uses a write-semaphore/read-semaphore signaling protocol with a lock semaphore for multi-writer exclusion. This backend represents the C-level POSIX IPC primitives exposed to Python, serving as a baseline for what is achievable without custom synchronization logic.
\end{itemize}

\section{Scenarios}
\label{sec:bench_scenarios}

Four scenario categories evaluate different aspects of IPC performance:

\begin{itemize}
    \item \textbf{Latency (1:1)}: A single producer communicates with a single consumer. This baseline scenario isolates raw IPC overhead without contention or fan-out effects.

    \item \textbf{Scalability (1:10)}: One writer distributes data to ten readers simultaneously. This pattern represents a camera feed shared among multiple processing pipelines (e.g., object detection, lane tracking, depth estimation running in parallel).

    \item \textbf{Contention (10:1)}: Ten writers send data to a single reader. This fan-in pattern models multiple sensors feeding a single aggregator or fusion module.

    \item \textbf{Size scaling (1--32~MiB)}: Single producer--consumer communication with varying payload sizes, from 1~MiB to 32~MiB. This reveals how performance degrades as messages approach and exceed the L3 cache capacity (32~MiB on the test system).
\end{itemize}

RsIpc (copy) achieves the lowest median latency at 0.19~ms, 9.4$\times$ lower than \texttt{multiprocessing.Queue} and 3.8$\times$ lower than MpPipe. The advantage stems from its minimal critical section: serialization occurs entirely outside the lock, which is held only for a single \texttt{memcpy} ($\sim$2~\textmu s). The reported throughput (22{,}104~MiB/s) exceeds the naive estimate $\text{size}/\text{p50} \approx 13{,}900$~MiB/s by a factor of 1.6$\times$, reflecting writer-reader overlap: the writer enqueues the next message while the reader deserializes the current one.

PosixIpc follows at 0.24~ms with the best determinism ratio (1.04). In the uncontended 1:1 case, POSIX named semaphores provide signaling efficiency comparable to futexes, and the absence of competing writers eliminates fairness concerns.

RsIpc (zerocopy) and MpShm cluster near 0.85~ms, as both perform pickle serialization while holding a lock. The difference (0.83 vs.\ 0.86~ms) is within measurement noise, confirming that pickle serialization dominates over synchronization overhead.

ZeroMQ achieves moderate latency (1.20~ms) but the highest throughput at 8,459~MiB/s in this scenario (a 3.8$\times$ pipelining factor). Its internal message queue provides deep pipelining (the most aggressive of any backend tested), explaining both its throughput advantage and its elevated determinism ratio~(1.67): buffered messages experience variable queuing delays.

Section~\ref{sec:rust_microbench} decomposes these latencies to isolate the IPC mechanism from serialization overhead.

\subsection{Determinism and Predictability}
\label{subsec:determinism_results}

Figure~\ref{fig:determinism} presents the determinism ratio (p99/p50) for each backend across the core scenarios.

\begin{figure}[htbp]
    \centering

    \label{fig:determinism}

In the 1:1 and 1:10 scenarios, all backends maintain determinism ratios below 2.1$\times$, with RsIpc (zerocopy) achieving 1.11--1.18$\times$ in both cases. The stability in these scenarios stems from the absence of writer contention: a single writer never competes for its own lock.

The contention scenario (10:1) differentiates the backends sharply. Three groups emerge:
\begin{enumerate}
    \item \textbf{Bounded} (determinism $< 4\times$): PosixIpc at 1.85$\times$, ZeroMQ at 1.97$\times$, RsIpc (copy) at 2.46$\times$, and MpQueue at 3.01$\times$.
    \item \textbf{Degraded} (determinism $10$--$20\times$): MpShm at 17.70$\times$, caused by Python's \texttt{Condition.wait(timeout)} polling with 10~ms granularity.
    \item \textbf{Catastrophic} (determinism $> 100\times$): RsIpc (zerocopy) at 106.5$\times$ and MpPipe at 118.7$\times$, caused by long critical sections under heavy contention (visible as the long tails in Figure~\ref{fig:latency_cdf}).
\end{enumerate}

For real-time applications, predictable latency is often more critical than minimal average latency. A system with p50 = 2~ms and p99 = 4~ms (ratio 2$\times$) is preferable to one with p50 = 0.85~ms and p99 = 91~ms (ratio 107$\times$) because the former permits tighter deadline budgeting.

Three distinct regimes emerge from the size-scaling data:

\textbf{Small messages (1--2~MiB)}: RsIpc (zerocopy) achieves 18,256--18,480~MiB/s, far exceeding all other backends (2,000--4,800~MiB/s). The zerocopy path reads directly from shared memory without an intermediate buffer, avoiding the cache pollution that a temporary allocation causes. All other backends cluster near 3,000--3,900~MiB/s at 1~MiB because per-message fixed overhead (lock acquisition, signaling, function call dispatch) dominates the small \texttt{memcpy} cost.

\textbf{Medium messages (4--8~MiB)}: The shared-memory copy backends (RsIpc copy, MpShm, PosixIpc) exhibit an abrupt throughput increase between 2 and 4~MiB, from roughly 3,300 to 10,000--16,000~MiB/s. Two factors contribute. First, the iteration count decreases from 100 (at 2~MiB) to 66 (at 4~MiB) due to the scaling formula described in Section~\ref{sec:bench_methodology}; fewer iterations reduce total test duration and thus the probability of OS scheduling interference amortized into the measurement. Second, at 4~MiB the shared memory region crosses the threshold for transparent huge pages: the library explicitly requests THP via \texttt{madvise(MADV\_HUGEPAGE)} on the mapped region, and the test environment is configured with THP set to \texttt{always} (Table~\ref{tab:environment}). At 4~MiB the kernel backs the region with two 2~MiB pages, reducing TLB misses during the \texttt{memcpy} from $\sim$1024 (with 4~KiB pages) to 2. Neither factor affects pipe-based backends (MpQueue, MpPipe), which remain capped at 2,600--3,800~MiB/s due to kernel buffer management overhead. RsIpc (zerocopy) peaks at 21,115~MiB/s at 4~MiB.

\textbf{Large messages (16--32~MiB)}: Performance degrades for all shared-memory backends. At 32~MiB the working set equals the L3 cache capacity, so writing and reading a single message evicts the entire cache. All shared-memory backends converge: RsIpc (zerocopy) at 3,403~MiB/s, PosixIpc at 3,536~MiB/s, and MpShm at 3,340~MiB/s, all bounded by DRAM bandwidth. Pipe-based mechanisms degrade further (MpQueue 1,576~MiB/s, MpPipe 1,593~MiB/s) due to additional kernel-mediated copies.

ZeroMQ exhibits erratic throughput across sizes (2,029 $\rightarrow$ 4,823 $\rightarrow$ 2,910 $\rightarrow$ 1,651 $\rightarrow$ 3,033 $\rightarrow$ 1,943~MiB/s), likely reflecting internal buffer management thresholds and the interaction between message framing overhead and kernel socket buffer sizes.


\section{Analysis: Copy vs.\ Zero-Copy Trade-off}
\label{sec:copy_vs_zerocopy}

Neither mode dominates across all scenarios. Their relative performance depends on communication topology and payload characteristics.

\subsection{When Each Mode Excels}

The two modes differ by a factor of $\sim$400$\times$ in lock hold duration when used with pickle (Table~\ref{tab:copy_vs_zerocopy}), which directly determines their contention behavior.

\textbf{Copy mode is optimal for}:
\begin{itemize}
    \item \textbf{Pickle-based workloads in 1:1 or N:1 patterns}: Copy mode achieves 0.19~ms latency in 1:1 and maintains bounded tail latency (4.52~ms p99) even under 10:1 contention.
    \item \textbf{Fan-in architectures}: The 2~\textmu s critical section ensures that multiple writers can cycle through the lock without causing starvation. The determinism ratio remains below 2.5$\times$ regardless of writer count.
\end{itemize}

\textbf{Zerocopy mode is optimal for}:
\begin{itemize}
    \item \textbf{Pre-serialized data}: When the payload is already a contiguous byte buffer (e.g., a raw NumPy array or a pre-encoded video frame), the zerocopy write path performs a single large \texttt{memcpy} identical in duration to copy mode, but avoids allocating a temporary buffer. The size-scaling results confirm this: at 4~MiB with raw byte payloads, RsIpc (zerocopy) achieves 21,115~MiB/s versus 15,931~MiB/s for copy mode.

    \item \textbf{Fan-out patterns (1:N)}: In the 1:10 scalability scenario, zerocopy achieves 1.36$\times$ higher throughput than copy mode (2,511 vs.\ 1,851~MiB/s) and 1.34$\times$ lower latency (1.97 vs.\ 2.64~ms). Multiple readers access shared memory concurrently through read guards without requiring per-reader copies.

    \item \textbf{Memory-constrained environments}: Copy mode requires allocating a temporary buffer equal to the serialized message size. For large payloads or systems with limited memory headroom, zerocopy eliminates this allocation entirely.
\end{itemize}

\label{sec:rust_microbench}

All measurements use 50 samples with 2-second measurement windows. The test system is the same as described in Section~\ref{sec:bench_methodology}.

\texttt{write\_waiting}, $N$=10 & 22.8 & 36\% \\

Two results stand out. First, a concurrent reader that the writer does not wait for (\texttt{target\_read\_count}~=~0) adds no measurable overhead to the write path. The reader operates on a separate core and its access to the shared buffer does not invalidate the writer's cache lines during the write window. Second, scaling from 1 to 10 readers adds only 6~\textmu s, far less than the 16.8~\textmu s baseline. Since readers execute concurrently, the writer waits for the \emph{slowest} reader rather than the sum of all readers. The observed 36\% increase reflects atomic contention on the \texttt{ReadersStateCount} field (CAS retries under concurrent increments) and condvar notification cost, not serialized read time.

\subsection{Read Path}

The \texttt{read\_fast\_path} benchmark measures the reader's cost in isolation: a background writer produces messages continuously, and the benchmarked thread reads and accesses the full 1~MiB payload. Since data is always available, the reader never enters the condvar wait path.

The measured read latency is \textbf{25.3~\textmu s}, approximately 50\% higher than a pure write (16.8~\textmu s). The additional cost comes from the read guard protocol: an atomic increment of \texttt{active\_}\allowbreak\texttt{readers} before accessing data, followed by a decrement of \texttt{active\_}\allowbreak\texttt{readers}, increment of \texttt{data\_}\allowbreak\texttt{consumed}, and a conditional \texttt{futex\_}\allowbreak\texttt{wake\_all} to signal the writer. These four atomic read-modify-write operations add roughly 8~\textmu s over the raw \texttt{memcpy} cost. This overhead is constant regardless of payload size: the same CAS operations execute whether the payload is 64~KiB or 16~MiB, making the read guard protocol negligible for large messages.

\section{Discussion}
\label{sec:bench_discussion}

\subsection{Where rs\_ipc Excels}

Three areas emerge where \texttt{rs\_ipc} provides clear advantages:

\textbf{Multi-reader scalability}: In the 1:10 scenario, RsIpc (zerocopy) achieves 5.5$\times$ higher throughput than ZeroMQ, 4.8$\times$ higher than MpShm, and 3.0$\times$ higher than PosixIpc. The lock-free version-checking mechanism allows readers to detect new messages without acquiring any lock, reducing contention on the critical path. The scalability ratio (1:10 latency / 1:1 latency) is 2.4$\times$ for RsIpc (zerocopy) compared to 19$\times$ for PosixIpc and 8.1$\times$ for ZeroMQ.

\textbf{Copy mode latency and predictability}: RsIpc (copy) achieves the lowest median latency in the 1:1 scenario (0.19~ms) and maintains determinism ratios below 2.5$\times$ even under 10:1 writer contention (p99 = 4.52~ms). In the 1:10 scenario, zerocopy mode is faster (1.97 vs.\ 2.64~ms), but copy mode remains the safest general-purpose choice for pickle-based workloads due to its bounded worst-case behavior across all topologies.

\textbf{Raw throughput for pre-serialized data}: For raw byte buffers, RsIpc (zerocopy) achieves 18,000--21,000~MiB/s in the 1--8~MiB range. At small sizes (1--2~MiB), this represents a 4.7$\times$ advantage over the next-best backend; at medium sizes (4--8~MiB), other shared-memory backends (RsIpc copy, MpShm) reach 12,000--16,000~MiB/s, narrowing the gap to 1.3--1.4$\times$. RsIpc (zerocopy) achieves the highest throughput at every size tested below 32~MiB.

\subsection{Critical Weakness: Zerocopy Under Writer Contention}

The zerocopy mode's catastrophic tail latency under writer contention---a determinism ratio of 106.5$\times$ (p99 = 90.87~ms) in the 10:1 scenario---warrants detailed analysis of the failure mode and its scope.

\textbf{Root cause}: The buffer-protocol serialization path holds the \texttt{FutexLock} for approximately 800~\textmu s per write. With ten concurrent writers, the lock becomes a severe bottleneck. The futex spin-then-block strategy provides no fairness guarantee: after the spin phase fails, all waiting writers enter the kernel wait queue, where wakeup order depends on scheduler state rather than arrival order, allowing repeated starvation of individual writers.

\textbf{Comparison with copy mode}: Under identical conditions, RsIpc (copy) achieves a p99 of 4.52~ms---20$\times$ better---because its 2~\textmu s critical section limits maximum queuing to approximately 9 $\times$ 2~\textmu s = 18~\textmu s per lock cycle. The remaining latency (up to 4.52~ms) reflects serialization time outside the lock plus scheduling overhead.

\textbf{Comparison with PosixIpc}: PosixIpc achieves the best contention determinism (1.85$\times$, p99 = 4.38~ms) despite using a conceptually similar approach. The advantage stems from POSIX semaphores implementing kernel-level FIFO wait queues, which guarantee bounded wait time regardless of contention level. The \texttt{FutexLock}'s lack of fairness is an intentional design choice that favors throughput in the common case (few writers) at the expense of worst-case behavior under heavy contention.

\textbf{Scope}: This vulnerability is specific to the combination of (1) multiple concurrent writers and (2) serialization inside the write guard. It does not affect:
\begin{itemize}
    \item Single-writer topologies (1:1, 1:N), where no lock contention exists.
    \item Pre-serialized data (raw bytes), where the lock hold time is $\sim$2~\textmu s regardless of mode.
    \item The read path, which uses lock-free version checking and concurrent access.
\end{itemize}

\subsection{Positioning Against External Libraries}

\textbf{ZeroMQ} is a general-purpose messaging library optimized for distributed systems and network transparency. In local single-machine IPC it is 5.0$\times$ (1:10) to 6.3$\times$ (1:1) slower in latency than the fastest \texttt{rs\_ipc} mode. Its strengths---multi-transport support, language-agnostic wire protocol, built-in patterns (PUB/SUB, REQ/REP)---are not relevant for the single-machine, Python-to-Python use case that \texttt{rs\_ipc} targets.

\textbf{PosixIpc} represents the hand-built POSIX approach: \texttt{shm\_open} with named semaphores, no higher-level abstraction. It achieves competitive 1:1 latency (0.24~ms, second only to RsIpc copy) and the best contention fairness (1.85$\times$ determinism). However, it lacks multi-reader scalability: its 1:10 latency (4.64~ms) is 2.4$\times$ worse than RsIpc (zerocopy), and adding readers requires manual per-reader semaphore management.

\texttt{rs\_ipc} occupies the niche of \textbf{high-throughput, multi-reader local IPC} with built-in synchronization and Rust memory safety. It provides higher-level semantics than raw POSIX primitives (automatic versioning, partial-blocking policies, concurrent reader access) without the overhead of general-purpose messaging frameworks.

\subsection{Limitations}

\begin{enumerate}
    \item \textbf{Zerocopy contention vulnerability}: As analyzed in the preceding subsection, zerocopy mode is unsuitable for fan-in (N:1) patterns with pickle serialization. Users must select copy mode for such topologies.

    \item \textbf{32~MiB cache degradation}: At payload sizes equal to or exceeding the L3 cache (32~MiB), all shared-memory backends converge to similar performance (3,300--3,500~MiB/s), bounded by DRAM bandwidth. The synchronization advantages of \texttt{rs\_ipc} become irrelevant when the memory subsystem is the bottleneck.

    \item \textbf{Platform restriction}: The futex-based synchronization is Linux-specific. Portability to other operating systems would require alternative synchronization backends (e.g., Windows \texttt{WaitOnAddress}, macOS \texttt{os\_unfair\_lock}), potentially with different performance characteristics.

    \item \textbf{Mode selection complexity}: The choice between copy and zerocopy modes depends on topology, payload type, and latency requirements, a design burden that simpler libraries (e.g., \texttt{multiprocessing.\allowbreak{}Queue}) do not impose.
\end{enumerate}

\subsection{Threats to Validity}
\label{subsec:threats_validity}

\textbf{Internal validity.}

\begin{enumerate}
    \item \textbf{Clock precision and monotonicity}: Latency measurements use \texttt{time.perf\_\-counter()}, which maps to \texttt{clock\_gettime(\allowbreak{}CLOCK\_MONOTONIC)} on Linux with sub-microsecond resolution. This clock is immune to NTP step adjustments that could produce negative or artificially inflated deltas. Since all processes execute on a single machine, they share one kernel clock source, eliminating inter-process clock synchronization as a concern.

    \item \textbf{CPU migration}: Writer and reader processes are pinned to dedicated physical cores via \texttt{os.sched\_setaffinity()}, preventing the OS scheduler from migrating processes between cores during measurement. This eliminates cache invalidation artifacts from cross-core migration and ensures consistent memory access latencies. For the 10:1 contention scenario (11 processes on 8 physical cores), pinning is automatically disabled; the resulting scheduler interference is reflected in the reported tail latencies for that scenario.

    \item \textbf{Thermal throttling}: The CPU governor is set to \texttt{performance} mode (Table~\ref{tab:environment}), which locks the CPU at base frequency and disables dynamic frequency scaling. Each trial includes 20 warmup iterations to bring caches, branch predictors, and TLB entries to steady state before measurement begins. The multi-trial design (10 independent trials with median reporting) further reduces the impact of transient thermal events on reported results.

    \item \textbf{Background processes}: Measurements are collected on a single-purpose workstation with no concurrent user workloads. However, kernel threads, systemd services, and hardware interrupt processing are not eliminated (no \texttt{isolcpus} kernel parameter). Their impact is bounded: in 10-trial median reporting, sporadic OS interference affects individual iterations but not the reported median, which requires a majority of trials to be affected before shifting.
\end{enumerate}

\textbf{External validity.}

\begin{enumerate}
    \item \textbf{Hardware generalizability}: Primary results are collected on AMD Zen~4 (Ryzen~7 7700). To assess whether findings are architecture-specific, the full benchmark suite is replicated on an Intel platform (Section~\ref{subsec:cross_platform}). The relative ordering of backends is consistent across architectures, though absolute latencies differ due to cache hierarchy and memory bandwidth characteristics.

    \item \textbf{Python-specific workload}: All Python-level measurements include pickle serialization overhead, which dominates the critical path (95\% of end-to-end latency, Table~\ref{tab:decomposition}). The relative performance of IPC mechanisms may differ for languages with cheaper serialization. The Rust microbenchmarks in Section~\ref{sec:rust_microbench} isolate the synchronization mechanism from serialization costs and demonstrate sub-microsecond overhead.

    \item \textbf{Payload representativeness}: The primary payload (2.64~MiB triple-channel image frame) represents computer vision pipelines. Applications with significantly different message sizes or access patterns may observe different relative performance. The size-scaling experiments (1--32~MiB) partially address this by evaluating across a range of payload sizes.
\end{enumerate}

\subsection{Design Guidelines}

The experimental results suggest the following implications for system designers:

\begin{enumerate}
    \item \textbf{Single-producer, single-consumer with pickle data}: Use RsIpc copy mode (Table~\ref{tab:latency_11}). It achieves 9.4$\times$ lower latency than \texttt{multiprocessing.Queue} and 3.8$\times$ lower than MpPipe, with minimal API complexity.

    \item \textbf{Fan-out architectures (1:N)}: Use RsIpc zerocopy mode (Table~\ref{tab:scalability_110}). It achieves the highest throughput (2,511~MiB/s) with strong latency predictability (1.18$\times$ determinism) in the 1:10 scenario.

    \item \textbf{Fan-in architectures (N:1)}: Use RsIpc copy mode exclusively (Table~\ref{tab:contention_101}). Zerocopy mode is unsuitable due to the 106.5$\times$ determinism ratio under writer contention.

    \item \textbf{Pre-serialized raw byte data (NumPy arrays, encoded video frames)}: Use RsIpc zerocopy mode regardless of topology (Table~\ref{tab:size_scaling}). With pre-serialized data, the lock hold time is $\sim$2~\textmu s (comparable to copy mode), and the zerocopy path achieves 18,000--21,000~MiB/s for messages up to 8~MiB.

    \item \textbf{When bounded worst-case latency is the primary concern}: Consider PosixIpc for its consistently low determinism ratios (1.04--1.85$\times$) across all scenarios, accepting the scalability trade-off in multi-reader patterns (Figure~\ref{fig:scalability_degradation}).
\end{enumerate}
