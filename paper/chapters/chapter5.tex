\subsection{Measurement Approach}

The benchmark framework employs true multiprocessing via Python's \texttt{spawn} start method, ensuring each participant runs in a separate process with its own address space. This reflects realistic deployment conditions where IPC is necessary precisely because threads cannot share state freely due to the GIL.

Startup synchronization uses a \texttt{multiprocessing.Barrier} so that all writer and reader processes begin their measurement loops simultaneously. Latency is measured end-to-end: the writer embeds a \texttt{time.time()} timestamp in each message immediately before transmission, and the reader computes the difference upon receipt. This captures the full IPC path including serialization, synchronization, memory transfer, and deserialization.

\subsection{Payload}

The primary payload is a \texttt{MockPipeData} structure containing three NumPy arrays of shape $640 \times 480 \times 3$ (unsigned 8-bit integers), representative of a triple-channel video frame from a computer vision pipeline. After pickle serialization, this payload occupies approximately 2.76~MB, corresponding to a single 640$\times$480 RGB frame---a common resolution in autonomous driving and robotics applications.

For size-scaling experiments, raw byte buffers of 1, 2, 4, 8, 16, and 32~MB are used to isolate the effect of payload size from serialization overhead.

\subsection{Metrics}

Four metrics characterize IPC performance:

\begin{itemize}
    \item \textbf{Median latency (p50)}: The 50th percentile of end-to-end message delivery time in milliseconds. Represents typical-case performance.

    \item \textbf{Tail latency (p99)}: The 99th percentile latency. Critical for real-time systems where worst-case behavior determines system feasibility.

    \item \textbf{Throughput}: Total bytes transferred divided by wall-clock duration, expressed in MB/s. Captures sustained transfer rate including synchronization overhead.

    \item \textbf{Determinism ratio}: Defined as $\text{p99} / \text{p50}$. A ratio of 1.0 indicates perfectly predictable latency; higher values indicate jitter. For real-time applications, predictable latency is often more valuable than lowest average latency.
\end{itemize}

\subsection{Statistical Methodology}

Each scenario executes 10 independent trials, with each trial performing 200 message iterations for the standard payload size. Iteration counts are scaled down for larger payloads to maintain reasonable execution time (e.g., approximately 12 iterations for 32~MB messages). Percentiles are computed per trial using NumPy's percentile function over all received messages per reader process. The reported values represent medians across trials, with first quartile (Q1) and third quartile (Q3) available for variability assessment.

When multiple readers participate, the reported p50 and p99 represent the arithmetic mean of per-reader percentiles within each trial. No warmup iterations are discarded; the barrier synchronization ensures that all processes begin measurement simultaneously, and the first few iterations capture cold-start behavior that is relevant to real deployments.

\subsection{Backends Under Test}

Seven IPC backends are evaluated, spanning Python's standard library, external libraries, and the two operational modes of \texttt{rs\_ipc}:

\begin{itemize}
    \item \textbf{RsIpc (zerocopy)}: The writer acquires a write guard and invokes \texttt{pickle.dump(obj, guard)}, serializing directly into shared memory via the Python buffer protocol. The reader acquires a read guard and calls \texttt{pickle.loads(guard)}, deserializing directly from shared memory. No intermediate copies are created.

    \item \textbf{RsIpc (copy)}: The writer serializes with \texttt{pickle.dumps(obj)} into a temporary Python bytes object, then calls \texttt{shm.write(bytes)} which performs a single \texttt{memcpy} into shared memory. The reader receives a Rust-allocated copy of the shared memory contents and deserializes from that copy.

    \item \textbf{multiprocessing.Queue}: Python's standard thread-safe, process-safe queue. Internally uses pipes with a background feeder thread for serialization. Bounded to size 1 for fair comparison with fixed-size shared memory slots.

    \item \textbf{multiprocessing.Pipe}: Low-level bidirectional connection using OS pipes. In multi-reader scenarios, a \texttt{multiprocessing.Lock} serializes writer access to prevent interleaved messages.

    \item \textbf{multiprocessing.shared\_memory (MpShm)}: Python's native shared memory module, supplemented with manual \texttt{multiprocessing.Lock} and \texttt{multiprocessing.Condition} for synchronization. This backend replicates what a developer would build using only the standard library, and serves as a direct comparison point for the synchronization quality of \texttt{rs\_ipc}.

    \item \textbf{ZeroMQ}: The \texttt{pyzmq} library using PUSH/PULL sockets over IPC transport (\texttt{ipc://} Unix domain sockets). Represents a mature, widely-deployed messaging library with internal threading, message framing, and batching optimizations. In multi-reader scenarios, one PUSH socket per reader ensures guaranteed delivery to all consumers.

    \item \textbf{PosixIpc}: The \texttt{posix\_ipc} package providing POSIX shared memory (\texttt{shm\_open}) with POSIX named semaphores (\texttt{sem\_open}) for synchronization. Uses a write-semaphore/read-semaphore signaling protocol with a lock semaphore for multi-writer exclusion. This backend represents the C-level POSIX IPC primitives exposed to Python, serving as a baseline for what is achievable without custom synchronization logic.
\end{itemize}


\section{Scenarios}
\label{sec:bench_scenarios}

Four scenario categories evaluate different aspects of IPC performance:

\begin{itemize}
    \item \textbf{Latency (1:1)}: A single producer communicates with a single consumer. This baseline scenario isolates raw IPC overhead without contention or fan-out effects.

    \item \textbf{Scalability (1:10)}: One writer distributes data to ten readers simultaneously. This pattern represents a camera feed shared among multiple processing pipelines (e.g., object detection, lane tracking, depth estimation running in parallel).

    \item \textbf{Contention (10:1)}: Ten writers send data to a single reader. This fan-in pattern models multiple sensors feeding a single aggregator or fusion module.

    \item \textbf{Size scaling (1--32~MB)}: Single producer--consumer communication with varying payload sizes, from 1~MB to 32~MB. This reveals how performance degrades as messages approach and exceed the L3 cache capacity (32~MiB on the test system).
\end{itemize}

RsIpc (copy) achieves the lowest median latency at 0.19~ms---9.3$\times$ faster than \texttt{multiprocessing.Queue} and 3.7$\times$ faster than MpPipe. ZeroMQ achieves moderate latency (1.20~ms) with relatively high throughput (8,459~MB/s). The throughput exceeds what latency alone would suggest because ZeroMQ's internal message queue enables pipelining: the sender enqueues the next message before the receiver finishes processing the current one. However, this buffering introduces latency variability (determinism ratio 1.67).

        MpPipe & 0.77 & 91.01 & 3,492 & 118.7 \\

        \hline
    \end{tabular}
\end{table}

The contention scenario produces the most striking results of the evaluation, revealing a critical architectural vulnerability in the zerocopy mode.

\textbf{RsIpc (zerocopy) exhibits catastrophic tail latency} with a p99 of 90.87~ms and a determinism ratio of 106.5$\times$. The root cause is the long critical section inherent to the buffer-protocol serialization path: each writer holds the \texttt{FutexLock} for approximately 800~\textmu s while \texttt{pickle.dump} executes hundreds of incremental writes through the buffer protocol interface. With ten writers contending for a single lock, this creates severe lock convoy effects. Writers that lose the initial CAS race transition the lock to the \texttt{CONTENDED} state and enter \texttt{futex\_wait}, where they are subject to kernel scheduling latency. The combination of 800~\textmu s critical sections and OS scheduling quantum boundaries (typically 1--10~ms on Linux CFS) produces the observed 90~ms tail.

\textbf{MpPipe exhibits a similar pathology} (p99 = 91.01~ms, determinism = 118.7$\times$). When ten writers simultaneously push 2.76~MB messages through OS pipes, the kernel pipe buffer fills, causing backpressure that interacts with the \texttt{multiprocessing.Lock} used to serialize writer access.

\textbf{RsIpc (copy) handles contention effectively} with a p99 of 4.52~ms and determinism of 2.46$\times$. Its critical section lasts only $\sim$2~\textmu s (a single \texttt{memcpy}), allowing the ten writers to cycle through the lock rapidly. Even in the \texttt{CONTENDED} state, the short hold time limits the worst-case queuing delay.

\textbf{PosixIpc achieves the best contention determinism} at 1.85$\times$. POSIX named semaphores implement kernel-level FIFO wait queues, providing inherent fairness that prevents writer starvation. This bounded ordering guarantee is absent from the futex spin-then-block strategy, which offers no fairness between competing waiters.

ZeroMQ shows the worst median latency (19.55~ms) but bounded determinism (1.97$\times$), as its internal mutex and message queue provide consistent---if slow---serialization of concurrent writers.

In the 1:1 and 1:10 scenarios, all backends maintain determinism ratios below 2.1$\times$, with RsIpc (zerocopy) achieving 1.11--1.18$\times$ in both cases. The stability in these scenarios stems from the absence of writer contention: a single writer never competes for its own lock.

The contention scenario (10:1) differentiates the backends sharply. Three groups emerge:
\begin{enumerate}
    \item \textbf{Bounded} (determinism $< 4\times$): PosixIpc at 1.85$\times$, ZeroMQ at 1.97$\times$, RsIpc (copy) at 2.46$\times$, and MpQueue at 3.01$\times$.
    \item \textbf{Degraded} (determinism $10$--$20\times$): MpShm at 17.70$\times$, caused by Python's \texttt{Condition.wait(timeout)} polling with 10~ms granularity.

\end{enumerate}

For real-time applications, predictable latency is often more critical than minimal average latency. A system with p50 = 2~ms and p99 = 4~ms (ratio 2$\times$) is preferable to one with p50 = 0.85~ms and p99 = 91~ms (ratio 107$\times$) because the former permits tighter deadline budgeting.

\section{Analysis: Copy vs.\ Zero-Copy Trade-off}
\label{sec:copy_vs_zerocopy}

The benchmark results reveal a nuanced trade-off between the two operational modes of \texttt{rs\_ipc}. Neither mode dominates across all scenarios; their relative performance depends critically on the communication topology and payload characteristics.

\subsection{Critical Section Analysis}

The fundamental difference between the two modes lies in their lock hold duration. Table~\ref{tab:critical_section} summarizes the execution paths.

\begin{table}[htbp]
    \centering
    \caption{Critical section comparison between copy and zerocopy modes.}
    \label{tab:critical_section}
    \begin{tabular}{lll}
        \hline
        \textbf{Phase} & \textbf{Copy Mode} & \textbf{Zerocopy Mode} \\
        \hline
        1. Serialize & \texttt{pickle.dumps(obj)} & (deferred to step 3) \\
          & $\sim$800~\textmu s, no lock held & \\
        2. Acquire lock & \texttt{start\_write()} & \texttt{write\_guard()} \\
          & via \texttt{FutexLock} & via \texttt{FutexLock} \\
        3. Transfer data & single \texttt{memcpy} & \texttt{pickle.dump(obj, guard)} \\
          & $\sim$2~\textmu s & $\sim$800~\textmu s, hundreds of \\
          & & incremental \texttt{.write()} calls \\
        4. Publish & sequence increment & sequence increment \\
        5. Release lock & drop guard & drop guard \\
        \hline
        \textbf{Lock hold time} & $\sim$2~\textmu s & $\sim$800~\textmu s \\
        \hline
    \end{tabular}
\end{table}

In copy mode, serialization occurs entirely outside the critical section. The writer calls \texttt{pickle.dumps(obj)} to produce a byte string in the Python heap (approximately 800~\textmu s for a 2.76~MB payload), then acquires the writer mutex and performs a single \texttt{ptr::copy\_nonoverlapping} to transfer the pre-serialized data into shared memory. The lock is held for approximately 2~\textmu s---just the duration of one \texttt{memcpy}.

In zerocopy mode, the writer first acquires the lock via \texttt{write\_guard()}, then calls \texttt{pickle.dump(obj, guard)}. The pickle protocol serializes the object through hundreds of incremental \texttt{.write()} calls to the guard's buffer protocol interface. Each call crosses the Python-to-Rust FFI boundary, performs a bounds check, and executes a small \texttt{memcpy} into shared memory. The lock is held throughout this entire process---approximately 800~\textmu s.

The ratio of lock hold times is approximately 400$\times$, which directly impacts contention behavior: in multi-writer scenarios, waiting writers must sleep for substantially longer when the zerocopy lock holder completes its serialization.

\subsection{When Each Mode Excels}

\textbf{Copy mode is optimal for}:
\begin{itemize}
    \item \textbf{Pickle-based workloads in 1:1 or N:1 patterns}: Copy mode achieves 0.19~ms latency in 1:1 and maintains bounded tail latency (4.52~ms p99) even under 10:1 contention.
    \item \textbf{Fan-in architectures}: The 2~\textmu s critical section ensures that multiple writers can cycle through the lock without causing starvation. The determinism ratio remains below 2.5$\times$ regardless of writer count.
\end{itemize}

\textbf{Zerocopy mode is optimal for}:
\begin{itemize}
    \item \textbf{Pre-serialized data}: When the payload is already a contiguous byte buffer (e.g., a raw NumPy array or a pre-encoded video frame), the zerocopy write path performs a single large \texttt{memcpy} identical in duration to copy mode, but avoids allocating a temporary buffer. The size-scaling results confirm this: at 4~MB with raw byte payloads, RsIpc (zerocopy) achieves 21,115~MB/s versus 15,931~MB/s for copy mode.

    \item \textbf{Fan-out patterns (1:N)}: In the 1:10 scalability scenario, zerocopy achieves 1.36$\times$ higher throughput than copy mode (2,511 vs.\ 1,851~MB/s) and 1.34$\times$ lower latency (1.97 vs.\ 2.64~ms). Multiple readers access shared memory concurrently through read guards without requiring per-reader copies.

    \item \textbf{Memory-constrained environments}: Copy mode requires allocating a temporary buffer equal to the serialized message size. For large payloads or systems with limited memory headroom, zerocopy eliminates this allocation entirely.
\end{itemize}

\subsection{Contention Vulnerability}

The 10:1 contention results expose a fundamental limitation of the zerocopy architecture when used with pickle serialization. With a determinism ratio of 106.5$\times$ (p99 = 90.87~ms vs.\ p50 = 0.85~ms), the zerocopy mode is \textbf{unsuitable for fan-in patterns with serialization inside the lock}.

The mechanism is straightforward: with ten writers each holding the lock for $\sim$800~\textmu s, the expected wait time for the last writer in a queue approaches 10 $\times$ 800~\textmu s = 8~ms for a single cycle. However, the observed 90~ms tail exceeds this estimate by an order of magnitude. The additional latency arises from the interaction between the \texttt{FutexLock}'s spin-then-block strategy and the OS scheduler: once a writer enters \texttt{futex\_wait} (state \texttt{CONTENDED}), its wakeup is subject to scheduling latency. Under heavy contention with 10 writer processes plus 1 reader process on an 8-core/16-thread system, context switch overhead and scheduling quantum boundaries compound the queuing delay.

This vulnerability does \textbf{not} apply to pre-serialized data (raw byte buffers), where the zerocopy lock hold time reduces to a single \texttt{memcpy}---comparable to copy mode. The issue is specific to the combination of (1) buffer-protocol serialization inside the write guard, and (2) multiple concurrent writers.


\section{Rust-Level Microbenchmarks}
\label{sec:rust_microbench}

To isolate the cost of the Rust synchronization layer from Python/PyO3/pickle overhead, Criterion microbenchmarks measure raw write throughput at the Rust level using a 1~MB payload.

\subsection{Benchmark Configuration}

Three benchmark functions evaluate different synchronization costs:

\begin{itemize}
    \item \textbf{\texttt{pure\_write}}: Writes 1~MB to shared memory with \texttt{target\_read\_count = 0} and no registered readers. Measures the raw write path: mutex acquisition, \texttt{memcpy}, sequence increment, mutex release.

    \item \textbf{\texttt{write\_no\_wait\_with\_reader}}: Same configuration as \texttt{pure\_write}, but with one registered reader consuming messages on a background thread. The writer does not wait for consumption (\texttt{target\_read\_count = 0}), so this measures the cost of concurrent reader access on the write path.

    \item \textbf{\texttt{write\_waiting\_with\_N\_readers}}: Configures \texttt{target\_read\_count = N} with $N$ active reader threads. The writer blocks in \texttt{start\_write()} until all $N$ readers have consumed the previous message. This measures the full synchronization cost including condvar signaling and wakeup latency.
\end{itemize}

Each benchmark uses Criterion's default configuration with 50 samples and 2-second measurement windows per sample.

\subsection{Expected Scaling Behavior}

The write-with-readers benchmarks reveal the synchronization cost as a function of reader count. With \texttt{target\_read\_count = N}, the writer must wait for the \texttt{data\_consumed} counter (packed in the \texttt{ReadersStateCount} atomic, as described in Chapter~\ref{chap:ch4}) to reach $N$ before proceeding. Each reader increments this counter upon completing its read, triggering a \texttt{futex\_wake\_all} on the writer's condvar.

The expected latency increase per additional reader is bounded by:
\begin{enumerate}
    \item The read duration (1~MB \texttt{memcpy} $\approx$ 100--200~\textmu s per reader, parallelized across cores).
    \item One \texttt{futex\_wake} system call per reader completion ($\approx$ 1~\textmu s each).
    \item The writer's spin-wait or \texttt{futex\_wait} to observe the counter update.
\end{enumerate}

Since readers operate concurrently, the total wait time scales with the slowest reader rather than the sum of all readers---a consequence of the partial-blocking design described in Section~\ref{sec:sync} of Chapter~\ref{chap:ch2}. However, cache contention on the \texttt{ReadersStateCount} atomic increases linearly with reader count due to the MESI invalidation traffic described in Section~\ref{subsec:false_sharing} of Chapter~\ref{chap:ch2}.


\section{Discussion}
\label{sec:bench_discussion}

\subsection{Where rs\_ipc Excels}

The benchmark results identify three areas where \texttt{rs\_ipc} provides clear advantages over existing IPC mechanisms:

\textbf{Multi-reader scalability}: In the 1:10 scenario, RsIpc (zerocopy) achieves 5.5$\times$ higher throughput than ZeroMQ, 4.8$\times$ higher than MpShm, and 3.0$\times$ higher than PosixIpc. The lock-free version-checking mechanism allows readers to detect new messages without acquiring any lock, reducing contention on the critical path. The scalability ratio (1:10 latency / 1:1 latency) is 2.4$\times$ for RsIpc (zerocopy) compared to 19$\times$ for PosixIpc and 8.1$\times$ for ZeroMQ.

\textbf{Copy mode latency and predictability}: RsIpc (copy) achieves the lowest median latency in the 1:1 scenario (0.19~ms) and maintains determinism ratios below 2.5$\times$ even under 10:1 writer contention (p99 = 4.52~ms). In the 1:10 scenario, zerocopy mode is faster (1.97 vs.\ 2.64~ms), but copy mode remains the safest general-purpose choice for pickle-based workloads due to its bounded worst-case behavior across all topologies.

\textbf{Raw throughput for pre-serialized data}: For raw byte buffers, RsIpc (zerocopy) achieves 18,000--21,000~MB/s in the 1--8~MB range. At small sizes (1--2~MB), this represents a 3.8--4.7$\times$ advantage over the next-best backend; at medium sizes (4--8~MB), other shared-memory backends (RsIpc copy, MpShm) reach 12,000--16,000~MB/s, narrowing the gap to 1.3--1.4$\times$. Nevertheless, RsIpc (zerocopy) consistently achieves the highest throughput at every size tested below 32~MB.

\subsection{Critical Weakness: Zerocopy Under Writer Contention}

The most significant finding of this evaluation is the catastrophic tail latency of zerocopy mode under writer contention: a determinism ratio of 106.5$\times$ (p99 = 90.87~ms) in the 10:1 scenario. This subsection analyzes the failure mode and its scope.

\textbf{Root cause}: The buffer-protocol serialization path holds the \texttt{FutexLock} for approximately 800~\textmu s per write. With ten concurrent writers, the lock becomes a severe bottleneck. The futex spin-then-block strategy provides no fairness guarantee: after the spin phase fails, all waiting writers enter the kernel wait queue, where wakeup order depends on scheduler state rather than arrival order. This allows repeated starvation of individual writers.

\textbf{Comparison with copy mode}: Under identical conditions, RsIpc (copy) achieves a p99 of 4.52~ms---20$\times$ better---because its 2~\textmu s critical section limits maximum queuing to approximately 9 $\times$ 2~\textmu s = 18~\textmu s per lock cycle. The remaining latency (up to 4.52~ms) reflects serialization time outside the lock plus scheduling overhead.

\textbf{Comparison with PosixIpc}: PosixIpc achieves the best contention determinism (1.85$\times$, p99 = 4.38~ms) despite using a conceptually similar approach. The advantage stems from POSIX semaphores implementing kernel-level FIFO wait queues, which guarantee bounded wait time regardless of contention level. The \texttt{FutexLock}'s lack of fairness is an intentional design choice that favors throughput in the common case (few writers) at the expense of worst-case behavior under heavy contention.

\textbf{Scope}: This vulnerability is specific to the combination of (1) multiple concurrent writers and (2) serialization inside the write guard. It does not affect:
\begin{itemize}
    \item Single-writer topologies (1:1, 1:N), where no lock contention exists.
    \item Pre-serialized data (raw bytes), where the lock hold time is $\sim$2~\textmu s regardless of mode.
    \item The read path, which uses lock-free version checking and concurrent access.
\end{itemize}

\subsection{Positioning Against External Libraries}

The inclusion of ZeroMQ and PosixIpc in the evaluation clarifies the positioning of \texttt{rs\_ipc} within the broader IPC ecosystem.

\textbf{ZeroMQ} represents a general-purpose messaging library optimized for distributed systems, network transparency, and protocol richness. In local single-machine IPC, it is 5.0$\times$ (1:10 scenario) to 6.3$\times$ (1:1 scenario) slower in latency than the fastest \texttt{rs\_ipc} mode for each scenario. Its strengths---multi-transport support, language-agnostic wire protocol, built-in patterns (PUB/SUB, REQ/REP)---are irrelevant for the single-machine, Python-to-Python use case that \texttt{rs\_ipc} targets.

\textbf{PosixIpc} represents the ``hand-built C approach'' to shared memory IPC: direct use of POSIX primitives without higher-level abstractions. It achieves competitive 1:1 latency (0.24~ms, second only to RsIpc copy) and the best contention fairness (1.85$\times$ determinism). However, it lacks the multi-reader scalability mechanisms of \texttt{rs\_ipc}: its 1:10 performance (4.64~ms) is 2.4$\times$ worse than RsIpc (zerocopy), and scaling requires manual per-reader semaphore management.

\texttt{rs\_ipc} occupies the niche of \textbf{high-throughput, multi-reader local IPC} with built-in synchronization and Rust safety guarantees. It provides higher-level semantics than raw POSIX primitives (automatic versioning, partial-blocking policies, concurrent reader support) without the overhead of general-purpose messaging frameworks.

\subsection{Limitations}

\begin{enumerate}
    \item \textbf{Zerocopy contention vulnerability}: As analyzed in the preceding subsection, zerocopy mode is unsuitable for fan-in (N:1) patterns with pickle serialization. Users must select copy mode for such topologies.

    \item \textbf{32~MB cache degradation}: At payload sizes equal to or exceeding the L3 cache (32~MiB), all shared-memory backends converge to similar performance (3,300--3,500~MB/s), bounded by DRAM bandwidth. The synchronization advantages of \texttt{rs\_ipc} become irrelevant when the memory subsystem is the bottleneck.

    \item \textbf{Platform restriction}: The futex-based synchronization is Linux-specific. Portability to other operating systems would require alternative synchronization backends (e.g., Windows \texttt{WaitOnAddress}, macOS \texttt{os\_unfair\_lock}), potentially with different performance characteristics.

    \item \textbf{Mode selection complexity}: The choice between copy and zerocopy modes depends on topology, payload type, and latency requirements. This places a design burden on the user that simpler libraries (e.g., \texttt{multiprocessing.Queue}) do not impose.
\end{enumerate}

\subsection{Design Guidelines}

Based on the evaluation results, the following guidelines assist developers in selecting an appropriate IPC strategy:

\begin{enumerate}
    \item \textbf{Single-producer, single-consumer with pickle data}: Use RsIpc copy mode. It achieves 9.3$\times$ lower latency than \texttt{multiprocessing.Queue} and 3.7$\times$ lower than MpPipe, with minimal API complexity.

    \item \textbf{Fan-out architectures (1:N, e.g., one camera feeding multiple pipelines)}: Use RsIpc zerocopy mode. It provides the best combination of throughput (2,511~MB/s) and latency predictability (1.18$\times$ determinism) in the 1:10 scenario.

    \item \textbf{Fan-in architectures (N:1, e.g., multiple sensors feeding one aggregator)}: Use RsIpc copy mode exclusively. Zerocopy mode is unsuitable due to the 106.5$\times$ determinism ratio under writer contention.

    \item \textbf{Pre-serialized raw byte data (NumPy arrays, encoded video frames)}: Use RsIpc zerocopy mode regardless of topology. With pre-serialized data, the lock hold time is $\sim$2~\textmu s (comparable to copy mode), and the zerocopy path achieves 18,000--21,000~MB/s for messages up to 8~MB.

    \item \textbf{When bounded worst-case latency is the primary concern}: Consider PosixIpc for its consistently low determinism ratios (1.04--1.85$\times$) across all scenarios, accepting the scalability trade-off in multi-reader patterns.
\end{enumerate}
