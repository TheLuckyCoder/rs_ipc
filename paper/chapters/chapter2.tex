\chapter{Foundations and Requirements}
\label{chap:ch2}

% Foundations: POSIX shm/mmap, synchronization primitives, futex subsystem

The design of a shared memory IPC library rests on operating system primitives for memory sharing and process synchronization. This chapter presents the foundational mechanisms that underpin the implementation described in Chapter~\ref{chap:ch4}: POSIX shared memory and memory-mapped I/O for establishing shared address spaces, synchronization primitives for coordinating concurrent access, and the Linux futex subsystem that enables efficient blocking without kernel-mediated lock objects. The chapter concludes by deriving the requirements that these foundations impose on the library's architecture.

\section{POSIX Shared Memory and Memory Mapping}
\label{sec:shm}

Unlike pipe-based or socket-based mechanisms that copy data through the kernel, shared memory allows multiple processes to access the same physical memory region directly.

\subsection{Shared Memory Objects}

The POSIX shared memory API provides two primary functions for managing shared memory objects: \texttt{shm\_open} and \texttt{shm\_unlink}~\cite{posix2017}. The \texttt{shm\_open} function creates or opens a named shared memory object, returning a file descriptor that can be used with standard file operations. On Linux, these objects reside in a \texttt{tmpfs} filesystem mounted at \texttt{/dev/shm}, backed entirely by RAM and swap.

The lifecycle of a shared memory object follows a create-size-map-use-unmap-unlink pattern:

\begin{enumerate}
    \item \texttt{shm\_open} creates the object and returns a file descriptor.
    \item \texttt{ftruncate} sets the size of the memory region.
    \item \texttt{mmap} maps the region into the process address space.
    \item Processes read and write directly to the mapped region.
    \item \texttt{munmap} removes the mapping from the process.
    \item \texttt{shm\_unlink} removes the named object from the filesystem.
\end{enumerate}

Named shared memory objects persist in the filesystem namespace until explicitly unlinked, independent of the processes that created them, enabling communication patterns where the producer and consumer processes do not share a parent-child relationship (unlike anonymous mappings created via \texttt{fork}).

\subsection{Memory-Mapped I/O}

The \texttt{mmap} system call maps a file descriptor (including shared memory objects) into the virtual address space of the calling process~\cite{kerrisk2010}. When invoked with the \texttt{MAP\_SHARED} flag, modifications made by one process become visible to all other processes that have mapped the same underlying object. The kernel ensures coherence through the page table mechanism: all mappings of the same physical page share the same underlying memory, so all processes observe the same physical memory without the kernel performing explicit data movement.

However, visibility at the memory level does not imply ordering guarantees at the instruction level. Modern processors may reorder memory operations for performance, meaning that a write performed by one process may not be observed in the expected order by another process. This gap between memory coherence and memory consistency motivates the synchronization mechanisms described in Section~\ref{sec:sync}.

\subsection{Translation Lookaside Buffer Considerations}

When a process accesses a mapped memory region, the CPU translates virtual addresses to physical addresses via the Translation Lookaside Buffer (TLB). For large shared memory regions, TLB misses degrade performance; huge pages (2~MiB on x86\_64) reduce this pressure by covering larger address ranges with fewer entries. However, explicit huge pages require \texttt{hugetlbfs} (incompatible with \texttt{shm\_open}), and Transparent Huge Pages requested via \texttt{madvise(MADV\_HUGEPAGE)} are advisory and unreliable for frequently created regions~\cite{thp_kernel_docs}.

\subsection{Shared Memory versus Message Passing}

Message-passing mechanisms (pipes, sockets, message queues) handle buffering and delivery on behalf of the application---and in Python's \texttt{multiprocessing} module also perform serialization---introducing kernel-mediated copies (typically two per transfer: into and out of the kernel buffer). Shared memory eliminates these copies entirely: both processes operate on the same physical memory, achieving true zero-copy semantics.

The cost of this efficiency is complexity. Shared memory provides no inherent ordering, synchronization, or notification mechanism. The application must explicitly coordinate access to prevent data races, detect when new data is available, and ensure that readers do not observe partially written messages. These requirements motivate the synchronization primitives described in the following section.


\section{Synchronization and Cache Effects}
\label{sec:sync}

When multiple processes share a memory region, concurrent access without coordination leads to data races. Correct shared memory IPC requires atomic operations for lock-free state checks, memory ordering constraints to ensure cross-core visibility of writes, and blocking primitives to avoid busy-waiting~\cite{herlihy2012}. Modern hardware provides atomic read-modify-write instructions (compare-and-swap (CAS), fetch-and-add) that guarantee indivisible updates to aligned words, and memory ordering semantics (Acquire, Release, SeqCst in the C++11 model~\cite{boehm2008}) that constrain the order in which stores by one core become observable to loads on another. These form the foundation of the lock-free read paths described in Chapter~\ref{chap:ch4}. The blocking primitives---futexes---are covered separately in Section~\ref{sec:futex}; this section focuses on the hardware-level cache effect most relevant to the memory layout decisions.

\subsection{False Sharing}
\label{subsec:false_sharing}

Multi-core processors maintain cache coherence at the granularity of cache lines (typically 64 bytes on x86\_64). When one core modifies any byte within a cache line, the coherence protocol invalidates copies of the \textit{entire line} held by other cores. Two logically independent variables that reside on the same cache line therefore exhibit \textit{false sharing}: a write to one variable forces all cores caching the other variable to re-fetch, even though it was not modified~\cite{herlihy2012}.

In shared memory IPC, false sharing is particularly damaging. Consider a structure where a write-mostly field (a sequence counter incremented by the producer) and a read-mostly field (a consumer count) occupy the same cache line. Every producer write invalidates the cache line on all consumer cores, forcing re-fetches of data they are only reading---not because the data changed, but because an adjacent field did.

The standard mitigation is to separate fields with different access patterns into distinct cache lines through explicit padding. Using 128-byte separation (two cache lines) provides additional protection against hardware prefetching on processors with adjacent-line prefetchers (documented on Intel~\cite{intel_opt_manual}; conservative for AMD Zen where prefetch behavior differs).


\section{The Linux Futex Subsystem}
\label{sec:futex}

Traditional Unix synchronization primitives such as System~V semaphores require a system call for every lock and unlock operation, regardless of whether contention exists. The POSIX threads (pthread) library improves upon this with userspace fast paths, but cross-process use introduces complexity. The mutex must be initialized with the \texttt{PTHREAD\_\-PROCESS\_\-SHARED} attribute, placed in shared memory, and accessed through the same C library implementation in all processes (the internal layout is not standardized across implementations).

The \textit{futex} (Fast Userspace Mutex) subsystem, introduced in Linux 2.5.7~\cite{franke2002}, addresses these limitations.

\subsection{Architecture}

A futex operates on a single 32-bit integer in userspace memory. The kernel associates a wait queue with the physical address of this integer, enabling cross-process synchronization without any shared library state. The two core operations are:

\begin{itemize}
    \item \texttt{futex\_wait(addr, expected)}: If the value at \texttt{addr} equals \texttt{expected}, the calling thread is added to the kernel wait queue and suspended. If the values differ, the call returns immediately. This atomic check-and-sleep prevents lost wakeups.

    \item \texttt{futex\_wake(addr, count)}: Wakes up to \texttt{count} threads waiting on the queue associated with \texttt{addr}.
\end{itemize}

The common case (acquiring an uncontended lock) requires only a userspace atomic CAS operation with no system call. The kernel is involved only when a thread must actually sleep (contended lock) or wake a sleeper (unlock with waiters), making futexes efficient for workloads where contention is infrequent.

\subsection{The Three-State Lock Pattern}

Drepper~\cite{drepper2005} describes an efficient mutex implementation using three states rather than the naive two-state (locked/unlocked) approach:

\begin{itemize}
    \item \textbf{State 0 (Unlocked)}: The lock is available.
    \item \textbf{State 1 (Locked, no waiters)}: The lock is held but no other thread is waiting for it.
    \item \textbf{State 2 (Locked, with waiters)}: The lock is held and at least one thread is blocked in the kernel waiting for it.
\end{itemize}

The distinction between states 1 and 2 is an optimization: when unlocking from state 1, the implementation knows no threads are waiting and skips the \texttt{futex\_wake} system call entirely, eliminating a syscall on every uncontended unlock. Only when unlocking from state 2 must the kernel be invoked to wake a waiter.

The lock acquisition sequence follows:

\begin{enumerate}
    \item Attempt a CAS from state 0 to state 1 (fast path, no syscall).
    \item If the CAS fails, spin briefly with relaxed loads, hoping the lock is released quickly.
    \item If spinning fails, transition the state to 2 (signaling that waiters exist) and call \texttt{futex\_wait}.
    \item Upon waking, retry acquisition from step 2 (spin, then attempt the lock in contended state).
\end{enumerate}

The spin phase (step 2) uses relaxed loads rather than CAS operations to avoid generating cache-line invalidations, reducing coherence traffic when multiple threads contend for the same lock.

\subsection{Cross-Process Synchronization}

Futex wait queues are keyed by physical memory address, not by virtual address or process identity~\cite{franke2002}. Because \texttt{mmap} with \texttt{MAP\_SHARED} causes distinct virtual addresses in separate processes to resolve to identical physical frames, a 32-bit futex variable placed in such a region is inherently cross-process: a \texttt{futex\_wake} issued by the producer resolves to the same kernel wait queue that the consumer's \texttt{futex\_wait} registered against.

Physical-address keying eliminates the initialization complexity of process-shared pthread mutexes: a futex-based lock in shared memory works correctly as soon as the memory is mapped---POSIX mandates that \texttt{ftruncate} zero-fills newly extended shared memory objects, satisfying the zero-initialization requirement---no constructor, no attribute configuration, no shared library dependency. The lock's state is entirely represented by a 4-byte integer, making it position-independent: any naturally aligned 4-byte region in shared memory can serve as a lock with no initialization beyond zero-filling.

\section{The Python Concurrency Model}
\label{sec:python_concurrency}

\subsection{The Global Interpreter Lock}

CPython employs a Global Interpreter Lock (GIL) that permits only one thread to execute Python bytecode at any given time~\cite{python_gil}. The GIL serializes CPU-bound threads, forcing data-intensive applications to use multiple processes for parallelism. Those processes then require efficient IPC to exchange data, creating the tension this work addresses.

\subsection{Releasing the GIL from Native Extensions}

Native extensions written in C, C++, or Rust can release the GIL while executing code that does not interact with Python objects. The CPython C~API provides the macros \texttt{Py\_BEGIN\_ALLOW\_THREADS} and \texttt{Py\_END\_ALLOW\_THREADS} for this purpose. In the Rust ecosystem, the PyO3 framework provides an equivalent mechanism through the \texttt{Python::detach()} method, called on the GIL token, which releases the GIL for the duration of the provided closure~\cite{pyo3}.

The safety invariant is that no Python objects may be accessed (read, written, or reference-counted) while the GIL is released. Code operating exclusively on Rust-owned data structures satisfies this invariant trivially.

\subsection{Free-Threading in Python 3.13+}

Python 3.13 introduced an experimental build configuration that removes the GIL (PEP~703)~\cite{pep703}, relying instead on biased reference counting and per-object locks. PEP~779~\cite{pep779}, accepted for Python~3.14, elevates free-threading from experimental to officially supported status. However, every C extension must explicitly declare compatibility; extensions that lack this declaration cause the interpreter to silently re-enable the GIL. Given the breadth of Python's extension ecosystem, widespread adoption is expected to require several years.

Crucially, free-threading addresses only \textit{intra-process} parallelism. Multi-process architectures remain necessary for fault isolation and independent resource limits, so IPC is not obsoleted. The GIL release patterns described in this work also remain beneficial: even without a global lock, blocking extensions must release the Python thread state via \texttt{py.detach()} so that interpreter-wide operations (stop-the-world garbage collection, biased reference count resolution) can proceed.

\section{Rust for Safe Systems Programming}
\label{sec:rust}

Rust is a systems programming language that provides memory safety and thread safety guarantees at compile time, without requiring a garbage collector or runtime~\cite{rustbook}. Its compile-time guarantees extend naturally to shared memory data structures that must be correct across process boundaries.

\subsection{Safety Guarantees}

Rust's ownership system prevents use-after-free, double-free, dangling pointers, and data races at compile time through single-ownership semantics and exclusive-or-shared borrowing rules~\cite{rustbook}. The \texttt{Send} and \texttt{Sync} marker traits extend these guarantees to concurrent programming; for shared memory structures, manually implementing \texttt{Sync} with an accompanying safety justification is the mechanism by which Rust verifies that concurrent access is correctly synchronized.

Operations the compiler cannot verify---raw pointer dereferencing, foreign function calls, manual \texttt{Sync} implementations---require the \texttt{unsafe} keyword~\cite{rustonomicon}. The convention is to encapsulate these within safe abstractions whose public API upholds the required invariants, achieving safety without runtime overhead.

\subsection{PyO3 and Foreign Function Interface}

PyO3 is a Rust framework for creating native Python extensions~\cite{pyo3}. It provides procedural macros that generate the CPython C~API boilerplate required to expose Rust functions, structures, and methods to Python. Key capabilities relevant to IPC include:

\begin{itemize}
    \item \textbf{GIL management}: The \texttt{Python<'py>} token represents GIL ownership. The \texttt{detach} method releases it for a closure's duration, enabling concurrent Python threads during blocking operations.

    \item \textbf{Buffer protocol}: Rust types can implement Python's buffer protocol, allowing Python code to access Rust-owned memory directly (e.g., through \texttt{memory\-view}) without copying.

    \item \textbf{Type conversions}: Automatic conversion between Python and Rust types at the FFI boundary, with zero-copy paths for bytes-like objects.
\end{itemize}

These capabilities are used extensively in Chapter~\ref{chap:ch4} to expose the shared memory protocol to Python.
