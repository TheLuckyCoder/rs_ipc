\subsection{Measurement Approach}

The benchmark framework uses Python's \texttt{spawn} start method, placing each participant in a separate process with its own address space---the deployment model where IPC is actually necessary. The overall methodology follows the guidelines of Georges et~al.~\cite{georges2007} for statistically rigorous performance evaluation: multiple independent trials, warmup iterations, and median reporting to reduce sensitivity to outliers.

\newpage
A \texttt{multiprocessing.Barrier} synchronizes startup so that all processes begin measurement simultaneously. 
Latency is measured end-to-end: the writer embeds a \texttt{time.perf\_counter()} timestamp in each message immediately before transmission, and the reader computes the difference upon receipt, capturing the full IPC path including serialization, synchronization, memory transfer, and deserialization. 
The \texttt{perf\_counter()} function maps to \texttt{clock\_gettime(CLOCK\_MONOTONIC)} on Linux~\cite{kerrisk2010}, providing sub-microsecond resolution immune to NTP adjustments. Since all processes execute on the same machine, they share a single kernel clock source, making cross-process timestamp differencing valid.

To eliminate measurement noise from CPU migration, writer and reader processes are pinned to dedicated physical cores using \texttt{os.sched\_setaffinity()}.
The writer occupies core~0; readers occupy cores~1 through~$N$.
Pinning is disabled when the total process count exceeds the number of logical threads reported by the operating system (\texttt{os.cpu\_count()}). On the primary test system (16 logical threads), all scenarios including 10:1 contention (11 processes) execute with pinning enabled. On systems with fewer threads, pinning is automatically disabled and processes share cores under OS scheduler control.

\subsection{Payload}

The primary payload is a \texttt{MockPipeData} structure containing three NumPy arrays of shape $640 \times 480 \times 3$ (unsigned 8-bit integers), representative of a triple-channel video frame from a computer vision pipeline. The raw data totals $640 \times 480 \times 3 \times 3 = 2{,}764{,}800$ bytes (2.64~MiB); after pickle serialization the message is marginally larger due to framing overhead.

For size-scaling experiments, raw byte buffers of 1, 2, 4, 8, 16, and 32~MiB are used to isolate the effect of payload size from serialization overhead.

\subsection{Metrics}

Four metrics characterize IPC performance:

\begin{itemize}
    \item \textbf{Median latency (p50)}: The 50th percentile of end-to-end message delivery time in milliseconds. Represents typical-case performance.

    \item \textbf{Tail latency (p99)}: The 99th percentile latency. Critical for real-time systems where worst-case behavior determines system feasibility.

    \item \textbf{Throughput}: Total bytes dispatched by all writers ($\text{payload\_size} \times \text{iterations} \times \text{num\_writers}$) divided by the wall-clock duration from the first writer's initial send to the last reader's final receive, expressed in MiB/s (binary megabytes). Because the writer can dispatch the next message while the reader deserializes the current one, sustained throughput under pipelining can significantly exceed the per-message estimate $\text{size} / \text{p50}$; the ratio between them quantifies each backend's pipelining efficiency.

    \item \textbf{Determinism ratio}: Defined as $\text{p99} / \text{p50}$. A ratio of 1.0 indicates perfectly predictable latency; higher values indicate jitter. For real-time applications, predictable latency is often more valuable than lowest average latency.
\end{itemize}

\subsection{Statistical Methodology}

Each scenario executes 10 independent trials. For the standard payload, each trial performs 200 message exchanges preceded by 20 warmup iterations whose latencies are discarded. Iteration counts scale down for larger payloads to keep execution time reasonable: $\lfloor 200 \,/\, (S / 2 + 1) \rfloor$ iterations for a message of $S$~MiB, yielding approximately 66 iterations at 4~MiB and 11 at 32~MiB. Percentiles are computed per trial using NumPy's percentile function with linear interpolation (the default method) over all post-warmup messages per reader process. The reported values represent medians across trials, with first quartile (Q1) and third quartile (Q3) available for variability assessment.

When multiple readers participate, the reported p50 and p99 represent the arithmetic mean of per-reader percentiles within each trial. This metric represents the mean reader experience rather than the system-wide latency distribution.

\subsection{Backends Under Test}

Seven IPC backends are evaluated, spanning Python's standard library, external libraries, and the two operational modes of \texttt{rs\_ipc}:

\begin{itemize}
    \item \textbf{RsIpc (zerocopy)}: The writer acquires a write guard and serializes directly into shared memory by calling \texttt{pickle.dump(obj, guard)}. The reader acquires a read guard and deserializes directly via \texttt{pickle.load(guard)}. No intermediate copies are created.

    \item \textbf{RsIpc (copy)}: The writer serializes with \texttt{pickle.dumps(obj)} into a temporary Python bytes object, then calls \texttt{shm.write(bytes)} which performs a single \texttt{memcpy} into shared memory. The reader receives a Rust-allocated copy of the shared memory contents and deserializes from that copy.

    \item \textbf{multiprocessing.Queue}: Python's standard thread-safe, process-safe queue. Internally uses pipes with a background feeder thread for serialization. Bounded to size 1 for fair comparison with fixed-size shared memory slots.

    \item \textbf{multiprocessing.Pipe}: Low-level bidirectional connection using OS pipes. In multi-reader scenarios, a \texttt{multiprocessing.Lock} serializes writer access to prevent interleaved messages.

    \item \textbf{multiprocessing.shared\_memory (MpShm)}: Python's native shared memory module, supplemented with manual \texttt{multi\-processing.\allowbreak{}Lock} and \texttt{multi\-processing.\allowbreak{}Condition} for synchronization. This backend replicates what a developer would build using only the standard library, and serves as a direct comparison point for the synchronization quality of~\texttt{rs\_ipc}.

    \item \textbf{ZeroMQ}: The \texttt{pyzmq} library~\cite{zeromq2013} using PUSH/PULL sockets over IPC transport (\texttt{ipc://} Unix domain sockets). Represents a mature, widely-deployed messaging library with internal threading, message framing, and batching optimizations. In multi-reader scenarios, one PUSH socket per reader ensures guaranteed delivery to all consumers.

    \item \textbf{PosixIpc}: The \texttt{posix\_ipc} package~\cite{posixipc_pkg} providing POSIX shared memory (\texttt{shm\_\allowbreak{}open}) with POSIX named semaphores (\texttt{sem\_\allowbreak{}open}) for synchronization. Uses a write-semaphore/read-semaphore signaling protocol with a lock semaphore for multi-writer exclusion. This backend represents the C-level POSIX IPC primitives exposed to Python, serving as a baseline for what is achievable without custom synchronization logic.
\end{itemize}

\section{Scenarios}
\label{sec:bench_scenarios}

Four scenario categories evaluate different aspects of IPC performance:

\begin{itemize}
    \item \textbf{Latency (1:1)}: A single producer communicates with a single consumer. This baseline scenario isolates raw IPC overhead without contention or fan-out effects.

    \item \textbf{Scalability (1:10)}: One writer distributes data to ten readers simultaneously. This pattern represents a camera feed shared among multiple processing pipelines (e.g., object detection, lane tracking, depth estimation running in parallel).

    \item \textbf{Contention (10:1)}: Ten writers send data to a single reader. This fan-in pattern models multiple sensors feeding a single aggregator or fusion module.

    \item \textbf{Size scaling (1--32~MiB)}: Single producer--consumer communication with varying payload sizes, from 1~MiB to 32~MiB. This reveals how performance degrades as messages approach and exceed the L3 cache capacity (32~MiB on the test system).
\end{itemize}

RsIpc (copy) achieves the lowest median latency at 0.19~ms, 8.9$\times$ lower than \texttt{multiprocessing.Queue} and 3.6$\times$ lower than MpPipe. The advantage stems from its minimal critical section: serialization occurs entirely outside the lock, which is held only for a single \texttt{memcpy} ($\sim$40~\textmu s for the 2.64~MiB payload). The reported throughput (22{,}278~MiB/s) exceeds the naive estimate $\text{size}/\text{p50} \approx 13{,}800$~MiB/s by a factor of 1.6$\times$, reflecting writer-reader overlap: the writer serializes its next message (outside the lock) while the reader deserializes the previous one (after releasing the read guard).

PosixIpc follows at 0.24~ms with a low median latency, though its p99 (0.39~ms) and determinism ratio (1.62) are elevated compared to RsIpc (copy). In the uncontended 1:1 case, POSIX named semaphores provide signaling efficiency comparable to futexes for median latency, but occasional scheduling delays affect the tail.

MpShm and RsIpc (zerocopy) cluster near 0.83--0.84~ms, as both perform pickle serialization while holding a lock. The difference (0.83 vs.\ 0.84~ms) is within measurement noise, confirming that pickle serialization dominates over synchronization overhead.

ZeroMQ achieves moderate latency (1.68~ms) with throughput of 6{,}017~MiB/s (a 3.8$\times$ pipelining factor). Its internal message queue provides pipelining that overlaps send and receive operations, explaining both its throughput relative to median latency and its elevated determinism ratio~(1.48): buffered messages experience variable queuing delays.

Section~\ref{sec:rust_microbench} decomposes these latencies to isolate the IPC mechanism from serialization overhead.

In the 1:1 and 1:10 scenarios, all backends maintain determinism ratios below 2.2$\times$, with RsIpc (zerocopy) achieving 1.09--1.14$\times$ in both cases. The stability in these scenarios stems from the absence of writer contention: a single writer never competes for its own lock.

The contention scenario (10:1) differentiates the backends sharply. Three groups emerge:
\begin{enumerate}
    \item \textbf{Bounded} (determinism $< 3\times$): PosixIpc at 1.33$\times$, ZeroMQ at 1.84$\times$, RsIpc (copy) at 1.81$\times$, and MpQueue at 2.85$\times$.
    \item \textbf{Degraded} (determinism $20$--$30\times$): MpShm at 29.3$\times$, caused by Python's \texttt{Condition.wait(timeout)} polling with 10~ms granularity.
    \item \textbf{Catastrophic} (determinism $> 90\times$): RsIpc (zerocopy) at 90.1$\times$ and MpPipe at 95.5$\times$, caused by long critical sections under heavy contention (visible as the long tails in Figure~\ref{fig:latency_cdf}).
\end{enumerate}

For real-time applications, predictable latency is often more critical than minimal average latency. A system with p50 = 2~ms and p99 = 4~ms (ratio 2$\times$) is preferable to one with p50 = 0.87~ms and p99 = 78~ms (ratio 90$\times$) because the former permits tighter deadline budgeting.

Three distinct regimes emerge from the size-scaling data:

\textbf{Small messages (1--2~MiB)}: RsIpc (zerocopy) achieves 17,485--18,353~MiB/s, far exceeding all other backends (2,000--3,900~MiB/s). The zerocopy path reads directly from shared memory without an intermediate buffer, avoiding the cache pollution that a temporary allocation causes. All other backends cluster near 3,000--3,900~MiB/s at 1~MiB because per-message fixed overhead (lock acquisition, signaling, function call dispatch) dominates the small \texttt{memcpy} cost.

\textbf{Medium messages (4--8~MiB)}: The shared-memory copy backends (RsIpc copy, MpShm, PosixIpc) exhibit an abrupt throughput increase between 2 and 4~MiB, from roughly 3,300 to 10,000--16,000~MiB/s. Two factors complicate interpretation of the 4~MiB throughput data. First, the iteration count decreases from 100 (at 2~MiB) to 66 (at 4~MiB) due to the scaling formula described in Section~\ref{sec:bench_methodology}; fewer iterations reduce the probability of OS scheduling interference in the measurement, potentially producing cleaner medians. Second, and dominantly, at 4~MiB the shared memory region crosses the threshold for transparent huge pages: the library explicitly requests THP via \texttt{madvise(MADV\_HUGEPAGE)} on the mapped region, and the test environment is configured with THP set to \texttt{always} (Table~\ref{tab:environment}). At 4~MiB the kernel backs the region with two 2~MiB pages, reducing TLB misses during the \texttt{memcpy} from $\sim$1024 (with 4~KiB pages) to 2. A controlled experiment with THP disabled (\texttt{/sys/kernel/mm/transparent\_hugepage/enabled} set to \texttt{never}) confirms this mechanism: at 4~MiB without THP, RsIpc (copy) achieves only 3{,}309~MiB/s (identical to its 2~MiB performance), MpShm drops from 15{,}371 to 3{,}329~MiB/s, and PosixIpc drops from 10{,}146 to 3{,}204~MiB/s. The throughput jump is entirely attributable to THP activation. Neither factor affects pipe-based backends (MpQueue, MpPipe), which remain capped at 2,600--3,900~MiB/s due to kernel buffer management overhead. RsIpc (zerocopy) achieves peak throughput of 20,650~MiB/s at 8~MiB.

\textbf{Large messages (16--32~MiB)}: Performance degrades for all shared-memory backends. At 32~MiB the working set equals the L3 cache capacity, so writing and reading a single message evicts the entire cache. All shared-memory backends converge: RsIpc (zerocopy) at 3,398~MiB/s, PosixIpc at 3,503~MiB/s, and MpShm at 3,265~MiB/s, all bounded by DRAM bandwidth. Pipe-based mechanisms degrade further (MpQueue 1,625~MiB/s, MpPipe 1,618~MiB/s) due to additional kernel-mediated copies.

ZeroMQ exhibits erratic throughput across sizes (2,243 $\rightarrow$ 2,288 $\rightarrow$ 1,166 $\rightarrow$ 3,272 $\rightarrow$ 3,245 $\rightarrow$ 1,482~MiB/s), likely reflecting internal buffer management thresholds and the interaction between message framing overhead and kernel socket buffer sizes.


\section{Analysis: Copy vs.\ Zero-Copy Trade-off}
\label{sec:copy_vs_zerocopy}

Neither mode dominates across all scenarios. Their relative performance depends on communication topology and payload characteristics.

\subsection{When Each Mode Excels}

The two modes differ by a factor of $\sim$400$\times$ in lock hold duration when used with pickle (Table~\ref{tab:copy_vs_zerocopy}), which directly determines their contention behavior.

\textbf{Copy mode is optimal for}:
\begin{itemize}
    \item \textbf{Pickle-based workloads in 1:1 or N:1 patterns}: Copy mode achieves 0.19~ms latency in 1:1 and maintains bounded tail latency (3.35~ms p99) even under 10:1 contention.
    \item \textbf{Fan-in architectures}: The $\sim$40~\textmu s critical section (memcpy only, $\sim$20$\times$ shorter than zerocopy pickle) ensures that multiple writers can cycle through the lock without starvation. The determinism ratio remains below 1.9$\times$ regardless of writer count.
\end{itemize}

\textbf{Zerocopy mode is optimal for}:
\begin{itemize}
    \item \textbf{Pre-serialized data}: When the payload is already a contiguous byte buffer (e.g., a raw NumPy array or a pre-encoded video frame), the zerocopy write path performs a single large \texttt{memcpy} identical in duration to copy mode, but avoids allocating a temporary buffer. The size-scaling results confirm this: at 4~MiB with raw byte payloads, RsIpc (zerocopy) achieves 19,988~MiB/s versus 15,652~MiB/s for copy mode.

    \item \textbf{Fan-out patterns (1:N)}: In the 1:10 scalability scenario, zerocopy achieves 1.37$\times$ higher throughput than copy mode (2,545 vs.\ 1,857~MiB/s) and 1.34$\times$ lower latency (1.93 vs.\ 2.60~ms). Multiple readers access shared memory concurrently through read guards without requiring per-reader copies.

    \item \textbf{Memory-constrained environments}: Copy mode requires allocating a temporary buffer equal to the serialized message size. For large payloads or systems with limited memory headroom, zerocopy eliminates this allocation entirely.
\end{itemize}

\section{Rust-Level Microbenchmarks}
\label{sec:rust_microbench}

The Python-level benchmarks in the preceding sections measure end-to-end latency including pickle serialization, PyO3 type conversion, and GIL management. To decompose these costs, this section isolates the Rust synchronization and memory-copy overhead using Criterion microbenchmarks that bypass Python entirely.

All measurements use 50 samples with 2-second measurement windows. The test system is the same as described in Section~\ref{sec:bench_methodology}.

\subsection{Write Path and Reader Scaling}

Table~\ref{tab:rust_write_scaling} reports the write latency for a 1~MiB payload under increasing reader counts. Each reader thread performs a blocking read and accesses the full payload buffer before releasing its read guard.

\begin{table}[htbp]
\centering
\caption{Write latency for 1~MiB payload as a function of reader count.}
\label{tab:rust_write_scaling}
\begin{tabular}{lrr}
\toprule
\textbf{Benchmark} & \textbf{Latency (\textmu s)} & \textbf{Overhead vs.\ pure write} \\
\midrule
\texttt{pure\_write} (no readers) & 16.8 & --- \\
\texttt{write\_no\_wait} (1 reader, target=0) & 16.4 & $\approx$0\% \\
\texttt{write\_waiting}, $N$=1 & 16.8 & $<$1\% \\
\texttt{write\_waiting}, $N$=2 & 19.3 & 15\% \\
\texttt{write\_waiting}, $N$=3 & 19.8 & 18\% \\
\texttt{write\_waiting}, $N$=5 & 20.3 & 21\% \\
\texttt{write\_waiting}, $N$=10 & 22.8 & 36\% \\
\bottomrule
\end{tabular}
\end{table}

Two results stand out. First, a concurrent reader that the writer does not wait for (\texttt{target\_read\_count}~=~0) adds no measurable overhead to the write path. The reader operates on a separate core and its access to the shared buffer does not invalidate the writer's cache lines during the write window. Second, scaling from 1 to 10 readers adds only 6~\textmu s, far less than the 16.8~\textmu s baseline. Since readers execute concurrently, the writer waits for the \emph{slowest} reader rather than the sum of all readers. The observed 36\% increase reflects atomic contention on the \texttt{ReadersStateCount} field (CAS retries under concurrent increments) and condvar notification cost, not serialized read time.

\subsection{Read Path}

The \texttt{read\_fast\_path} benchmark measures the reader's cost in isolation: a background writer produces messages continuously, and the benchmarked thread reads and accesses the full 1~MiB payload. Since data is always available, the reader never enters the condvar wait path.

The measured read latency is \textbf{25.3~\textmu s}, approximately 50\% higher than a pure write (16.8~\textmu s). The additional cost comes from the read guard protocol: an atomic increment of \texttt{active\_}\allowbreak\texttt{readers} before accessing data, followed by a decrement of \texttt{active\_}\allowbreak\texttt{readers}, increment of \texttt{data\_}\allowbreak\texttt{consumed}, and a conditional \texttt{futex\_}\allowbreak\texttt{wake\_all} to signal the writer. These four atomic read-modify-write operations add roughly 8~\textmu s over the raw \texttt{memcpy} cost. This overhead is constant regardless of payload size: the same CAS operations execute whether the payload is 64~KiB or 16~MiB, making the read guard protocol negligible for large messages.

\subsection{Payload Size Scaling}

Table~\ref{tab:rust_size_scaling} shows the write-with-one-reader roundtrip time across payload sizes. This benchmark uses \texttt{target\_read\_count}~=~1, measuring the time from write start to the point where the single reader has consumed the message and the writer can proceed again.

\begin{table}[htbp]
\centering
\caption{Write roundtrip latency and effective memory bandwidth by payload size (1 reader, target=1).}
\label{tab:rust_size_scaling}
\begin{tabular}{rrr}
\toprule
\textbf{Payload Size} & \textbf{Latency (\textmu s)} & \textbf{Bandwidth (GiB/s)} \\
\midrule
64 KiB & 1.2 & 52.1 \\
256 KiB & 3.7 & 67.6 \\
1 MiB & 17.5 & 55.9 \\
4 MiB & 73.3 & 53.3 \\
16 MiB & 443.8 & 35.2 \\
\bottomrule
\end{tabular}
\end{table}

Below 4~MiB, latency scales linearly with size, confirming that \texttt{memcpy} dominates over synchronization overhead. The effective bandwidth of 52--68~GiB/s reflects that both the write and the read access the same physical memory region, benefiting from L3 cache residency at smaller sizes. At 16~MiB the working set (write plus read of the same region) reaches the L3 cache capacity, forcing partial main memory accesses and reducing bandwidth to 35~GiB/s.

The data fits a linear model $t(s) = C_\text{fixed} + s / \text{BW}$ where $C_\text{fixed} \approx 1.5$~\textmu s represents the per-message synchronization cost (lock acquire, sequence CAS, condvar notify, lock release) and $\text{BW} \approx 55$~GiB/s represents the effective memory bandwidth for cache-resident payloads. Substituting: at 1~MiB the model predicts $1.5 + 1024^2 / (55 \times 2^{30}) \approx 19.3$~\textmu s, consistent with the measured 17.5~\textmu s. The model breaks down above 4~MiB as cache eviction reduces effective bandwidth, but confirms that for payloads below L3 capacity, synchronization overhead is negligible ($< 10\%$ at 64~KiB, $< 1\%$ at 1~MiB).

\subsection{Overhead Decomposition}

These microbenchmarks enable a layered decomposition of the Python-level 1:1 latency. The Python benchmark reports a median latency of 840~\textmu s for \texttt{rs\_ipc} (zerocopy) with the 2.64~MiB pickle payload. Table~\ref{tab:decomposition} attributes this cost across the software stack.

\begin{table}[htbp]
\centering
\caption{Latency decomposition for the zerocopy 1:1 path (2.64~MiB pickle payload).}
\label{tab:decomposition}
\begin{tabular}{llrr}
\toprule
\textbf{Layer} & \textbf{Component} & \textbf{Latency (\textmu s)} & \textbf{\% of total} \\
\midrule
Python & \texttt{pickle.dump} (serialize) & $\sim$406 & 48.3 \\
Python & \texttt{pickle.load} (deserialize) & $\sim$392 & 46.7 \\
Rust & Memory transfer (write + read) & $\sim$30 & 3.6 \\
Rust & Synchronization (lock, CAS, notify) & $<$2 & $<$0.3 \\
FFI & PyO3 dispatch + GIL release/acquire & $\sim$10 & 1.2 \\
\midrule
& \textbf{Total} & $\sim$840 & 100 \\
\bottomrule
\end{tabular}
\end{table}

The memory transfer estimate derives from the \texttt{pure\_write} benchmark: at 1~MiB, the write path (lock + \texttt{memcpy} + publish) completes in 16.8~\textmu s. Subtracting the synchronization overhead ($<$2~\textmu s, see below) gives approximately 15~\textmu s per MiB of \texttt{memcpy} bandwidth. For the 2.64~MiB benchmark payload, write and read together transfer approximately 30~\textmu s of raw memory access (extrapolated from the per-MiB rate, accounting for L3 cache residency in the zerocopy path where pickle performs incremental accesses). The synchronization upper bound follows from comparing \texttt{pure\_write} (16.8~\textmu s) with \texttt{write\_waiting} $N$=1 (16.8~\textmu s): the writer waiting for a single reader to consume adds no measurable overhead beyond the \texttt{memcpy} itself, bounding all atomic operations (lock acquire, sequence CAS, condvar notify, lock release) to less than 2~\textmu s. The PyO3 residual accounts for Python-to-Rust function dispatch, type conversion, and GIL state transitions.

The decomposition confirms that \textbf{95\% of end-to-end latency originates in the Python serialization layer}, not the IPC transport. The Rust mechanism contributes approximately 32~\textmu s of the 840~\textmu s total. This result explains why the zerocopy mode with raw byte buffers (Table~\ref{tab:size_scaling}) achieves 17,000--21,000~MiB/s: bypassing pickle eliminates the dominant cost entirely, leaving only the memory transfer and sub-microsecond synchronization on the critical path.

\section{Discussion}
\label{sec:bench_discussion}

\subsection{Where rs\_ipc Excels}

Three areas emerge where \texttt{rs\_ipc} provides clear advantages:

\textbf{Multi-reader scalability}: In the 1:10 scenario, RsIpc (zerocopy) achieves 6.8$\times$ higher throughput than ZeroMQ, 4.6$\times$ higher than MpShm, and 3.2$\times$ higher than PosixIpc. The lock-free version-checking mechanism allows readers to detect new messages without acquiring any lock, reducing contention on the critical path. The scalability ratio (1:10 latency / 1:1 latency) is 2.3$\times$ for RsIpc (zerocopy) compared to 20.1$\times$ for PosixIpc and 6.5$\times$ for ZeroMQ.

\textbf{Copy mode latency and predictability}: RsIpc (copy) achieves the lowest median latency in the 1:1 scenario (0.19~ms) and maintains determinism ratios below 1.9$\times$ even under 10:1 writer contention (p99 = 3.35~ms). In the 1:10 scenario, zerocopy mode achieves lower latency (Table~\ref{tab:scalability_110}), but copy mode remains the safest general-purpose choice for pickle-based workloads due to its bounded worst-case behavior across all topologies.

\textbf{Raw throughput for pre-serialized data}: For raw byte buffers, RsIpc (zerocopy) achieves 17,000--21,000~MiB/s in the 1--8~MiB range. At small sizes (1--2~MiB), this represents a 4.5$\times$ advantage over the next-best backend; at medium sizes (4--8~MiB), other shared-memory backends (RsIpc copy, MpShm) reach 12,000--16,000~MiB/s, narrowing the gap to 1.3$\times$. RsIpc (zerocopy) achieves the highest throughput at every size tested below 32~MiB.

\subsection{Critical Weakness: Zerocopy Under Writer Contention}

The zerocopy mode's catastrophic tail latency under writer contention---a determinism ratio of 90.1$\times$ (p99 = 77.95~ms) in the 10:1 scenario---warrants detailed analysis of the failure mode and its scope.

\textbf{Root cause}: The buffer-protocol serialization path holds the \texttt{FutexLock} for approximately 800~\textmu s per write. With ten concurrent writers, the lock becomes a severe bottleneck. The futex spin-then-block strategy provides no fairness guarantee~\cite{drepper2005}: after the spin phase fails, all waiting writers enter the kernel wait queue, where wakeup order depends on scheduler state rather than arrival order, allowing repeated starvation of individual writers.

\textbf{Comparison with copy mode}: Under identical conditions, RsIpc (copy) achieves a p99 of 3.35~ms---23$\times$ better---because its $\sim$40~\textmu s critical section (memcpy of the 2.64~MiB payload; see Section~\ref{sec:rust_microbench}) limits maximum lock queuing to approximately 9~$\times$~40~\textmu s $\approx$~360~\textmu s. The remaining latency (up to 3.35~ms) is dominated by the reader consumption wait---the writer holds the mutex while waiting for the single reader to finish its read cycle between messages---plus serialization time outside the lock and scheduling overhead.

\textbf{Comparison with PosixIpc}: PosixIpc achieves the best contention determinism (1.33$\times$, p99 = 3.19~ms) despite using a conceptually similar approach. The advantage stems from POSIX semaphores implementing kernel-level FIFO wait queues, which guarantee bounded wait time regardless of contention level. The \texttt{FutexLock}'s lack of fairness is an intentional design choice that favors throughput in the common case (few writers) at the expense of worst-case behavior under heavy contention.

\textbf{Scope}: This vulnerability is specific to the combination of (1) multiple concurrent writers and (2) serialization inside the write guard. It does not affect:
\begin{itemize}
    \item Single-writer topologies (1:1, 1:N), where no lock contention exists.
    \item Pre-serialized data (raw bytes), where both modes hold the lock only for the \texttt{memcpy} duration ($\sim$15~\textmu s per MiB).
    \item The read path, which uses lock-free version checking and concurrent access.
\end{itemize}

\subsection{Positioning Against External Libraries}

\textbf{ZeroMQ} is a general-purpose messaging library optimized for distributed systems and network transparency. In local single-machine IPC it is 5.6$\times$ (1:10) to 8.8$\times$ (1:1) slower in latency than the fastest \texttt{rs\_ipc} mode. Its strengths---multi-transport support, language-agnostic wire protocol, built-in patterns (PUB/SUB, REQ/REP)---are not relevant for the single-machine, Python-to-Python use case that \texttt{rs\_ipc} targets.

\textbf{PosixIpc} represents the hand-built POSIX approach: \texttt{shm\_open} with named semaphores, no higher-level abstraction. It achieves competitive 1:1 latency (0.24~ms, second only to RsIpc copy) and the best contention fairness (1.33$\times$ determinism). However, it lacks multi-reader scalability: its 1:10 latency (4.87~ms) is 2.5$\times$ worse than RsIpc (zerocopy), and adding readers requires manual per-reader semaphore management.

\texttt{rs\_ipc} occupies the niche of \textbf{high-throughput, multi-reader local IPC} with built-in synchronization and Rust memory safety. It provides higher-level semantics than raw POSIX primitives (automatic versioning, partial-blocking policies, concurrent reader access) without the overhead of general-purpose messaging frameworks.

Three observations emerge from the cross-platform data:

\textbf{Relative ordering is preserved.} On all three platforms, RsIpc (copy) achieves the lowest 1:1 median latency among \texttt{rs\_ipc} modes, and RsIpc (zerocopy) achieves the best scalability in the 1:10 scenario. The ranking of backends against external libraries (PosixIpc, ZeroMQ, MpQueue) is consistent across architectures.

\textbf{Absolute latencies scale with memory bandwidth.} The Ryzen~7~7700 (DDR5-6000) achieves 0.19~ms copy-mode latency; the Core~i5-10400F (DDR4-2133) reaches 0.87~ms---a 4.6$\times$ difference attributable primarily to the 2.8$\times$ memory bandwidth gap and the older microarchitecture's higher cache latencies. The Ryzen~9~5900HX (DDR4-3200) falls between at 0.75~ms.

\textbf{Determinism ratios remain bounded.} All platforms maintain determinism ratios below 1.7$\times$ in both the 1:1 and 1:10 scenarios, confirming that the low-jitter behavior of the futex-based synchronization is not an artifact of a specific hardware configuration.

\subsection{Limitations}

\begin{enumerate}
    \item \textbf{Zerocopy contention vulnerability}: As analyzed in the preceding subsection, zerocopy mode is unsuitable for fan-in (N:1) patterns with pickle serialization. Users must select copy mode for such topologies.

    \item \textbf{32~MiB cache degradation}: At payload sizes equal to or exceeding the L3 cache (32~MiB), all shared-memory backends converge to similar performance (3,200--3,500~MiB/s), bounded by DRAM bandwidth. The synchronization advantages of \texttt{rs\_ipc} become irrelevant when the memory subsystem is the bottleneck.

    \item \textbf{Platform restriction}: The futex-based synchronization is Linux-specific. Portability to other operating systems would require alternative synchronization backends (e.g., Windows \texttt{WaitOnAddress}, macOS \texttt{os\_unfair\_lock}), potentially with different performance characteristics.

    \item \textbf{Mode selection complexity}: The choice between copy and zerocopy modes depends on topology, payload type, and latency requirements, a design burden that simpler libraries (e.g., \texttt{multiprocessing.\allowbreak{}Queue}) do not impose.
\end{enumerate}

\subsection{Threats to Validity}
\label{subsec:threats_validity}

\textbf{Internal validity.}

\begin{enumerate}
    \item \textbf{Clock precision and monotonicity}: Latency measurements use \texttt{time.perf\_\-counter()}, which maps to \texttt{clock\_gettime(\allowbreak{}CLOCK\_MONOTONIC)} on Linux with sub-microsecond resolution. This clock is immune to NTP step adjustments that could produce negative or artificially inflated deltas. Since all processes execute on a single machine, they share one kernel clock source, eliminating inter-process clock synchronization as a concern.

    \item \textbf{CPU migration}: Writer and reader processes are pinned to dedicated logical threads via \texttt{os.sched\_setaffinity()}, preventing the OS scheduler from migrating processes between cores during measurement. This eliminates cache invalidation artifacts from cross-core migration and ensures consistent memory access latencies. On the primary test system (16 logical threads), all scenarios including 10:1 contention (11 processes) execute with pinning enabled; however, pinning to SMT siblings rather than distinct physical cores may introduce shared-resource contention that is absent in lower-process-count scenarios.

    \item \textbf{Thermal throttling}: The CPU governor is set to \texttt{performance} mode (Table~\ref{tab:environment}), which locks the CPU at base frequency and disables dynamic frequency scaling. Each trial includes 20 warmup iterations to bring caches, branch predictors, and TLB entries to steady state before measurement begins. The multi-trial design (10 independent trials with median reporting) further reduces the impact of transient thermal events on reported results.

    \item \textbf{Background processes}: Measurements are collected on a single-purpose workstation with no concurrent user workloads. However, kernel threads, systemd services, and hardware interrupt processing are not eliminated (no \texttt{isolcpus} kernel parameter). Their impact is bounded: in 10-trial median reporting, sporadic OS interference affects individual iterations but not the reported median, which requires a majority of trials to be affected before shifting.
\end{enumerate}

\textbf{External validity.}

\begin{enumerate}
    \item \textbf{Hardware generalizability}: Primary results are collected on AMD Zen~4 (Ryzen~7 7700). To assess whether findings are architecture-specific, the full benchmark suite is replicated on two additional platforms: an Intel Comet Lake desktop and an AMD Zen~3 laptop (Section~\ref{subsec:cross_platform}). The relative ordering of backends is consistent across architectures, though absolute latencies differ due to cache hierarchy and memory bandwidth characteristics.

    \item \textbf{Python-specific workload}: All Python-level measurements include pickle serialization overhead, which dominates the critical path (95\% of end-to-end latency, Table~\ref{tab:decomposition}). The relative performance of IPC mechanisms may differ for languages with cheaper serialization. The Rust microbenchmarks in Section~\ref{sec:rust_microbench} isolate the synchronization mechanism from serialization costs and demonstrate sub-microsecond overhead.

    \item \textbf{Payload representativeness}: The primary payload (2.64~MiB triple-channel image frame) represents computer vision pipelines. Applications with significantly different message sizes or access patterns may observe different relative performance. The size-scaling experiments (1--32~MiB) partially address this by evaluating across a range of payload sizes.
\end{enumerate}

\subsection{Design Guidelines}

The experimental results suggest the following implications for system designers:

\begin{enumerate}
    \item \textbf{Single-producer, single-consumer with pickle data}: Use RsIpc copy mode (Table~\ref{tab:latency_11}). It achieves 8.9$\times$ lower latency than \texttt{multiprocessing.Queue} and 3.6$\times$ lower than MpPipe, with minimal API complexity.

    \item \textbf{Fan-out architectures (1:N)}: Use RsIpc zerocopy mode (Table~\ref{tab:scalability_110}). It achieves the highest throughput (2,545~MiB/s) with strong latency predictability (1.14$\times$ determinism) in the 1:10 scenario.

    \item \textbf{Fan-in architectures (N:1)}: Use RsIpc copy mode exclusively (Table~\ref{tab:contention_101}). Zerocopy mode is unsuitable due to the 90.1$\times$ determinism ratio under writer contention.

    \item \textbf{Pre-serialized raw byte data (NumPy arrays, encoded video frames)}: Use RsIpc zerocopy mode regardless of topology (Table~\ref{tab:size_scaling}). With pre-serialized data, the lock hold time equals the \texttt{memcpy} duration (comparable to copy mode), and the zerocopy path achieves 17,000--21,000~MiB/s for messages up to 8~MiB.

    \item \textbf{When bounded worst-case latency is the primary concern}: Consider PosixIpc for its consistently low determinism ratios (1.28--1.62$\times$) across all scenarios, accepting the scalability trade-off in multi-reader patterns (Figure~\ref{fig:scalability_degradation}).
\end{enumerate}
